# TNSVT — User Flows

Generated by `/audit` and `/map`. Read-only.

A user flow describes the path a user takes to accomplish a goal, the screens they
touch, and the data they produce. These are derived from the current code (routes,
controllers, templates, entities) — not from wishful design.

---

## 1. Master journey (from MASTER-PROMPT-TNSVT.md)

```
Visitor
  → Public TNSVT
  → Register / Login
  → Sanctum
  → Learn
  → Practice
  → Plan
  → Trade
  → Journal
  → Guardian / Risk feedback
  → Review
  → Mentor / AI support
  → Improve
```

This journey is the **target**, not the current state. Audit findings:

- ✅ **Visitor → Public TNSVT** — `/` works (renders `public/home.html.twig`).
- ✅ **Register / Login** — `/login` renders `public/login.html.twig` (form only).
  Registration is **gap** (route exists in IA target, not implemented).
- ⚠️ **Sanctum** — `/sanctum` route not visible in audit; verify.
- ✅ **Learn** — `/campus`, `/api/academia/*` exist.
- ⚠️ **Practice** — no dedicated route. Probably means paper trading or demo.
  **Verify.**
- ⚠️ **Plan** — **gap**. No "Trading Plan" template.
- ⚠️ **Trade** — `/trading` is a legacy placeholder to tnsvt.com.
- ✅ **Journal** — `/journal` works, `JournalEntry` CRUD via API.
- ⚠️ **Guardian / Risk feedback** — atoms exist (`PropFirmAlert`,
  `NoTradeWindowService`), no unified surface.
- ✅ **Review** — Journal statistics (currently embedded in journal template).
- ⚠️ **Mentor / AI support** — no `MentorController`, no mentor role.
- ✅ **Improve** — implicit: re-plan, re-trade, re-journal.

## 2. Auth flow (real today)

```
[Anonymous]
   │
   ▼ GET /
HomeController::index()
   │
   ├── if authenticated → 302 /sanctum
   │
   └── if not           → render public/home.html.twig (landing)
                              │
                              ▼ user clicks "Entrar" in public nav
                              ▼ GET /login
                              HomeController::login()
                              │
                              └── if not authed → render public/login.html.twig
                                    │
                                    ▼ form submit
                                    POST /api/auth/login (JSON)
                                    │
                                    ├── success → localStorage tnsvt_user, redirect /sanctum or /journal
                                    └── failure → show error in #login-error
```

**Resolved (Phase 5):**
- Landing and login are now separate routes and templates. Visitor sees clean
  marketing on `/`, dedicated form on `/login`.

**Still to verify:**
- Logout uses `confirm()` and POST `/api/auth/logout`. No CSRF visible in the JS
  call (verify during `/security` audit).
- `localStorage.tnsvt_user` is used as a cache, not the source of truth. OK, but
  should not contain sensitive fields (verify).

## 4. Trading flow (today)

```
[/journal]
   │
   ▼ SanctumModuleController::journal
   render sanctum/journal.html.twig
   │
   ▼ inside, JS calls:
      GET  /api/journal/list        → list of JournalEntry
      POST /api/journal/save        → upsert JournalEntry
      POST /api/journal/sync        → batch sync
      GET  /api/journal/stats       → totals
      GET  /api/trading-accounts    → user's TradingAccount list
```

**Sub-flows:**

### 4.1 Record a trade

```
User clicks "+ New Trade" → modal opens
   │
   ▼ fill: asset, direction, date, entry, SL, TP, notes, photos
   ▼ POST /api/journal/save  (body = JournalEntry fields)
   │
   ├── success → close modal, refresh list, toast
   └── failure → show validation error
```

### 4.2 Sync offline

```
PWA queues writes in local IndexedDB
   │
   ▼ when online:
   POST /api/sync with payload {entries: [...]}
   │
   └── server applies LWW on updated_at per entity
```

### 4.3 View calendar

```
[/calendar]
   │
   ▼ SanctumModuleController::calendar
   render sanctum/calendar.html.twig
   │
   ▼ inside, JS calls:
      GET /api/calendar/events?tz=…&countries=…&impact=…
      GET /api/economic-reminder/list  (user's custom reminders)
      POST /api/economic-reminder/save
```

### 4.4 Connect to broker (cTrader)

```
[/api/ctrader/*]  ─ likely exists (entity CtraderConnection exists)
```

**Issue:** No Sanctum page surfaces "connect broker". Verify during `/integrate`.

### 4.5 PropFirm risk alert

```
PropFirmRuleChecker runs on Trade save
   │
   ├── if drawdown > threshold → POST /api/notifications + PropFirmAlert
   └── if daily loss > threshold → same
```

**Today's reality:** Service exists, but verify whether it is **invoked** from
the trade save flow. Audit open item.

### 6.5 Guardian (Phase 1 + 2 + 3 done)

```
[/sanctum/guardian]            ─ Phase 2 done (full page)
[/sanctum/dashboard]           ─ Phase 3 widget (compact score + top 3 signals)
[/journal]                     ─ Phase 3 banner (pre-trade warnings, risk.* only)
```

**Architecture:**

```
        ┌──────────────────────────┐
        │  TradeSavedEvent         │  ← dispatched by JournalController
        │  (entry, user, isNew)    │     SyncController
        └────────────┬─────────────┘
                     ▼
        ┌──────────────────────────┐
        │  GuardianSubscriber      │  ← push: evaluates PropFirm rules
        │  onTradeSaved()          │     creates PropFirmAlert entities
        └──────────────────────────┘
                     │
        ┌────────────▼─────────────┐
        │  PropFirmRuleChecker     │  ← existing service, now with
        │  getStatus() returns:    │     daily_loss_pct exposed
        │  drawdown, daily_loss,   │
        │  profit, status          │
        └────────────┬─────────────┘
                     ▼
        ┌──────────────────────────┐
        │  GuardianSignalCollector │  ← pull: aggregates on demand
        │  GuardianSignal DTO      │     for Guardian API endpoints
        │  DisciplineScore         │
        └────────────┬─────────────┘
                     ▼
        ┌──────────────────────────┐
        │  /api/guardian/*         │  ← consumed by Guardian page,
        │  /sanctum/dashboard      │     dashboard widget, journal banner
        │  /sanctum/journal banner │
        └──────────────────────────┘
```

**Phase 1 (API) + Phase 2 (UI page) + Phase 3 (event-driven push + dashboard
widget + journal banner + daily-loss signals) all done.** See
`INTEGRATION-NOTES.md` for the full build log.

Guardian should also expose **embedded widgets** in:

These widgets are **future work**, documented here, not implemented in `/audit`.

## 10. Cross-flow: Push notifications

When any of the above flows produces a server-side event (trade saved, alert
fired, message received, …), the flow is:

```
Domain event
   │
   ▼
Domain service (e.g., PropFirmRuleChecker)
   │
   ▼
Notification entity created
   │
   ▼
PushService → Firebase (kreait/firebase-php)
   │
   ▼
Mercure update → /api/notification/unread-count poll
   │
   ▼
Bell badge in shell.html.twig sidebar updates
```

This is the **output channel** of the Guardian concept.
