## ⚠️ Problemas encontrados

| # | Severidad | Problema | Impacto |
|---|---|---|---|
| 1 | 🔴 **Crítico** | **Logs de prod no se capturan** — Monolog va a `php://stderr` y Hostinger shared hosting no redirige stderr a un archivo. | Errores 500 son invisibles post-mortem; no se puede diagnosticar incidentes |
| 2 | 🟠 Alto | **`X-Powered-By: PHP/8.4.19` se filtra** en todas las respuestas. | Info disclosure menor (versión PHP visible para atacantes) |
| 3 | 🟠 Alto | **Auth bypass en `getCurrentUser()`** — el helper hace fallback a `user_code` desde query string o POST body sin validar identidad. Cualquiera con un user_code conocido puede ver el journal como "owner" sin autenticar. | Privacidad: lectura de journals ajenos si el user_code es adivinable |
| 4 | 🟠 Alto | **No hay backups automáticos** (Risk #7) — el cron no está instalado en hPanel. El usuario tiene que hacerlo manualmente. | Si una migration rompe prod, no hay rollback de datos posible |
| 5 | 🟡 Medio | **CSP usa `unsafe-inline`** para `script-src` y `style-src` (necesario para Stimulus + Twig, pero aumenta la superficie XSS). | Ataques XSS más fáciles de construir |
| 6 | 🟡 Medio | **`@error_log` en 20+ controllers** — suprime errores reales. | Errores se loguean pero el stack trace se pierde; debugging pobre |
| 7 | 🟡 Medio | **`/api/journal` retorna 400 sin auth** cuando falta `user_code` (no 401). | Confuso: parece error de input, no de auth |
| 8 | 🟡 Medio | **Login no devuelve headers `X-RateLimit-*`** (Limit, Remaining, Reset). | Cliente no sabe cuántas intentos le quedan antes del 429 |
| 9 | 🟢 Bajo | **Sin `Cache-Control` apropiado en `/api/auth/login`** — el response podría ser cacheado por proxies. | Teórico, sin impacto práctico |
| 10 | 🟢 Bajo | **Sin tests específicos de rate-limit / carga** (no validamos que el limitador funcione bajo carga real). | Cobertura incompleta |

## 🛠 Plan de remediación (priorizado)

### Fase 1 — Urgente (esta semana)

#### 1.1 Capturar logs en archivo (resuelve #1)
- **Cambio**: Cambiar `path: php://stderr` → `path: "%kernel.logs_dir%/prod.log"` en `config/packages/monolog.yaml`
- **Trade-off**: Los logs crecen en disco (estimado 5–50 MB/día). Necesitará rotación (rotating file handler).
- **Alternativa mejor**: Usar un servicio externo. **Sentry ya está configurado** en `config/packages/sentry.yaml` (release tracking) — basta con agregar `SENTRY_DSN` en `.env.local`.
- **Esfuerzo**: 30 min

#### 1.2 Quitar `X-Powered-By` header (resuelve #2)
- **Cambio**: En `public/index.php` agregar `header_remove('X-Powered-By');` al inicio, o en `.htaccess` (si existe) agregar `Header unset X-Powered-By`.
- **Esfuerzo**: 5 min

#### 1.3 Investigar auth bypass en `getCurrentUser()` (resuelve #3)
- **Acción**: Revisar si el fallback a `user_code` desde query string es intencional (legacy mobile app) o bug. Si es legacy, agregar logging de auditoría para detectar accesos anómalos.
- **Cambio recomendado**: Quitar el fallback — forzar siempre `X-Game-Code` header + signature (HMAC del código + timestamp).
- **Esfuerzo**: 2–3 h (incluye auditoría de uso real + tests)

### Fase 2 — Importante (próximas 2 semanas)

#### 2.1 Configurar backup cron en hPanel (resuelve #4)
- **Acción**: Documentar paso a paso para el usuario (manual, no automatizable desde código porque Hostinger deshabilita `proc_open` y `crontab`).
- **Riesgo**: Si el usuario no lo hace, prod sigue sin backup automático.
- **Mitigación**: Crear un recordatorio automático vía email/Slack cada vez que el endpoint `/api/health/migrations` detecte drift (correlacionar con Risk #3).
- **Esfuerzo**: 1 h (solo doc)

#### 2.2 Cambiar `@error_log` por `$logger->error()` (resuelve #6)
- **Cambio**: Inyectar `LoggerInterface` en todos los controllers que usan `@error_log` y reemplazar por `$logger->error($e->getMessage(), ['exception' => $e])`.
- **Archivos afectados** (muestra): `JournalController`, `CampusController`, `ChatController`, `FrequencyController`, `MusicController`, `CampusUploadController`.
- **Esfuerzo**: 4–6 h (incluye tests)

#### 2.3 Normalizar respuesta de auth faltante (resuelve #7)
- **Cambio**: En `/api/journal`, `/api/journal/stats`, etc. — cuando falta `user_code` en query y no hay header `X-Game-Code`, devolver **401** (con mensaje claro), no 400.
- **Razón**: 400 implica error del cliente en el input, 401 implica falta de autenticación. La línea divisoria importa para clientes HTTP.
- **Esfuerzo**: 1 h

### Fase 3 — Mejoras (este mes)

#### 3.1 CSP nonces (resuelve #5)
- **Cambio**: Usar `nonce-{random}` en lugar de `'unsafe-inline'` para scripts y styles críticos. Requiere cambios en Twig templates para inyectar el nonce en cada `<script>` y `<style>` inline.
- **Trade-off**: Más complejo; Stimulus necesita ser cargado con nonce (compatible).
- **Esfuerzo**: 1–2 días
- **Beneficio**: Defense-in-depth real contra XSS.

#### 3.2 Rate limit headers en login (resuelve #8)
- **Cambio**: Agregar `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` en `/api/auth/login`.
- **Implementación**: Hook en `AuthController::login` después de `checkAndHit()`, antes de retornar.
- **Esfuerzo**: 2 h

#### 3.3 Tests de carga del rate limiter (resuelve #10)
- **Agregar**: Test funcional que simule 100 requests en <60 s contra `/api/auth/login` y verifique que se aplica el `429 Too Many Requests` correctamente.
- **Esfuerzo**: 2–3 h

### Fase 4 — Nice to have

- **DB integrity check script** (`bin/check-db-integrity.sh`) — corre en CI semanal, valida foreign keys + índices huérfanos.
- **Sentry source maps** — para stack traces más claros en prod (requiere upload de sourcemaps en build step).
- **CSP nonce migration** (Fase 3.1 arriba).
- **Health dashboard en `/sanctum/monitoring`** — visualiza el estado de los 2 endpoints `/api/health/*` con históricos.
